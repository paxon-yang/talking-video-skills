# 方法层：怎么拆一条新的参考视频并复刻

这是 A/B/C/D 四条视频实际走过的流程，写成可照做的步骤。脚本都在本 Skill 的 `scripts/`（用途与依赖见 `scripts/README.md`），下文用 `$S` 代表 `~/.claude/skills/ae-motion-craft/scripts`。
工作目录约定：`<工程目录>/analysis/<研究名>/<视频代号>/`（原片 `src.mp4`、代理 `proxy.mp4`、拼图 `w/`、技法卡 `TECHNIQUES.md`）。原片只读。

```bash
S=~/.claude/skills/ae-motion-craft/scripts
W=<工程目录>/analysis/<研究名>/<代号>; mkdir -p $W/w && cd $W
```

## 1. 拿到可读素材
1. 先 `ffprobe` 看规格：`ffprobe -v error -show_entries stream=codec_type,width,height,r_frame_rate,avg_frame_rate,duration -of default=nw=1 src.mp4`
   - `r_frame_rate` 与 `avg_frame_rate` 不同 = 可变帧率（手机/屏幕录制常见）→ 必须做代理。
   - 记下原片帧率：24fps 的片子里「1 帧」= 1/24s，很多片子动画本身只有 12fps（C 就是），写数值时一律换算成秒。
2. **屏幕录制 / 超长合集 / 可变帧率 → 先做本地代理**（D 就是 19 分钟抖音录屏）：
   `$S/make_proxy.sh src.mp4 proxy.mp4 1280 30` → 恒定 30fps、1280 宽、每秒一个关键帧。19 分钟约 2.5 分钟。之后所有时间都是代理的秒数（帧号 = 秒 × 30）。
   - D 的代理是 1280×**722**（不是 720），写坐标时带上「@1280」。
   - 屏幕录制常常本来就没有声音（D 的代理只有视频轨），音频分析要用原片或另找音源。
3. 原片在云盘时先拷到本地工作目录再处理（云盘路径慢，且原片目录只读）。

## 2. 通览拼图（找东西在哪）
`$S/overview_sheet.sh src.mp4 w/ov 1 8 4 240` → `w/ov/sheet_001.jpg …` + `w/ov/index.txt`，用 Read 逐张看。
- 本机 ffmpeg **没有 drawtext**，图上没有时间码。时间按公式算：第 n 张、第 r 行、第 c 列（都从 1 数）
  `t = 起点 + ((n-1)·cols·rows + (r-1)·cols + (c-1)) / fps`，index.txt 里写着每张的起止时间。
- 这个时间有 ±1 个采样间隔误差（B 的 1fps 拼图最多偏 1.5s：标题「Code that's」实测 7.42s，拼图里在第 9 格）。**拼图只用来定位，写进技法卡的时间必须用 `-ss` 重新定位。**
- 长合集用 `fps=0.5`（每格 2 秒）先编目：D 的编目是 `c_NN.jpg`，16 格一张，`t = (k-1)·32 + 2·(p-1)`，误差 ±2–4s。
- 找硬切点（可选）：`ffmpeg -ss 10 -t 6 -i src.mp4 -vf "select='gt(scene,0.3)',showinfo" -f null - 2>&1 | grep -o 'pts_time:[0-9.]*'` → 输出的时间是相对 `-ss` 起点的，要加回去（A：输出 2.91 → 实际 12.91s，对上 A 的切点 12.913）

## 3. 编目 → 分组 → 深拆（分层策略与成本控制）
1. **编目**（便宜）：每段写「品牌/内容 · 大致秒数 · 看到的技法关键词」，再把所有技法去重成一张合并表（D 编目共 24 种）。
2. **分组**：按技法大类分成 2–4 组（D 分成 W1 光/几何/地图、W2 节点/路径/形变、W3 3D/合成/流体），一组交给一个子代理深拆。同时最多 3 个代理（8GB 内存 + 额度）。
3. **深拆**（贵）：只拆「定义质感」的那 10–20 个事件；每个事件一个窗口（0.5–3s）。3D/合成类先判可行性，再决定拆多深。
4. **先自行定位，别信编目时间**：编目误差可以很大——AutoClaw 编目写 640–702s，实际在 723–741s（偏约 80s）；Stash 偏约 -4s；Stellash 0–12s 只是终态预览，真构建过程在 31.07–34.7s；Pov 编目 800–832s，真正只有 811.0–832.7s。深拆第一步是在编目时间 ±60s 内用 1fps 拼图重新找到事件，写一张「编目 vs 实测」更正表放在技法卡开头。

## 4. 窗口内密集抽帧（看清每一步）
- 拼图：`$S/dense_sheet.sh proxy.mp4 w/d_pill.jpg 1042.2 1.0 30 6 320` → 第 k 格（从 0 数）`t = 起点 + k/fps`。
  - 12fps：看大致节奏；24/30fps（= 原片帧率）：看单帧细节、硬切、隔帧重复。时长 0.5–3s，格数 ≤60。
  - 局部放大：最后一个参数给 crop，如 `... 30 6 320 400:200:760:600`。
- 单帧 PNG（放大看、做对照）：`$S/extract_frames.sh src.mp4 w/fr 12.9 0.1 30 960` → 文件名是毫秒时间。
- 目视规则：数值前加「≈」= 估测；看不清就写「看不清」，不编。12fps 抽样意味着 <2 帧@24 的细节看不到。

## 5. 测量什么、怎么测（同一条命令既量原片也量我们的渲染）
`python3 $S/measure.py <子命令> <视频> --ss 起 --dur 长 --fps 采样 [--scale 480:270] [--crop w:h:x:y]`

| 想知道 | 量什么 | 命令 | 实例 |
|---|---|---|---|
| 缩放 / 显现宽度 | 亮（暗）像素外接框宽高 | `bbox --thr 150`；暗色字用 `--expr 'np.maximum(np.maximum(r,g),b)>100'` | A 标题 0.73s：`bbox src.mp4 --ss 0.7 --dur 0.1 --fps 30 --scale 960:540 --expr '…>100' --minfrac 0.002` → 宽 913/960 = 95.1%（与 VERIFY 一致） |
| 位移 / 滚动 / 平移速度 | 相邻帧互相关（行剖面或 2D） | `shift --axis y --max 20` | A 滚动：`shift src.mp4 --ss 26.6 --dur 2.4 --fps 30 --crop 960:600:480:420 --scale 480:300 --axis y --max 20` → 平台 -17px/帧（半尺寸）= 34px/帧@1080 |
| 模糊 → 清晰 | 水平相邻差、拉普拉斯方差（只比归一化时间） | `sharp` | A 卡 7 焦点拉回 |
| 淡入淡出 / 曝光 / 墨量 | 区域均值亮度、过阈值像素占比 | `region --crop … --thr 128 --dark` | D 屏幕点亮后桌面亮度 40 → 89 → 36 |
| 笔迹、彩色元素 | 颜色掩膜计数与外接框 | `color --expr '(r>150)&(g<110)&(b<110)&(r-g>60)'` | C 红笔：`color src.mp4 --ss 3.3 --dur 0.8 --fps 24 --scale 480:-2 --expr …` → 红像素 16,17,66,70,115,117,138,139（成对 = 12fps 动画），约 0.3s 画完圈 |
| 屏幕四角 | 亮区四角 | `screen_quad.py --thr 215 --crop …` | D 815s Pov |

**测量的坑（都踩过）：**
- **要裁出真正在动的区域**。A 滚动用整帧量出来是 0（固定的页眉和暗背景压住了），裁到报告正文才量出 34px/帧。
- 阈值会漏东西：A 标题用灰度>150 漏掉暗紫色字首，把缩放曲线夸大了；改用最大通道>100。
- 镜头同时在动时，元素自身的运动分不开（B 故障窗在镜头推进中长出来，条纹位移量不出；D 进度条填充因镜头旋转量不出）——如实写「测不了」。
- 代理分辨率不够时（D 的 6px 圆点、半调点径）就是看不清，别硬给数。
- `--scale` 后的像素要换算回原尺寸再写进卡，写明「px @1280」或「@1080」。

**判断缓动类型**：把一串等间隔采样值交给 `python3 $S/fit_decay.py "v0,v1,…" [--final 终值] --step-fps 采样fps`：
- 每步剩余比几乎恒定（离散度 <12%）→ 指数衰减 ease-out，脚本给出 k（换算到每帧@30）并对照 calm 0.84 / snappy 0.68。例：A 面板 `2.081,1.839,1.621,1.445,1.313,1.22,1.142 --final 1 --step-fps 15` → k=0.844/帧，calm。
- 增量恒定 → 线性；两头慢中间快 → ease-in-out，用 `node $S/fit_bezier.js "t0:v0,t1:v1,…"` 拟合 cubic-bezier（B 推近拟合 rmse 0.006）；越来越快然后一步占大头 → ease-in 接硬停（D pill：一步占总量 72%）。
- 成对相等 → 隔帧（on twos），按 2 帧一个样本重量；某一步占总量 >60% → 硬切/跳变。

## 6. 技法卡模板（每个事件一张，写进 TECHNIQUES.md）
```markdown
## 卡 N：<一句话名字>（t=起–止，帧号 f…）
| 字段 | 内容 |
|---|---|
| 时间 | 每个子事件的实测时间（-ss 定位，不用拼图时间） |
| 画面 | 看到什么（颜色写 #hex，尺寸写 px@宽度） |
| 构成（后→前） | 图层顺序 |
| 运动 | 逐帧数据（列出序列），注明「测」或「≈」 |
| 缓动 | 类型 + 参数（k / bezier / 线性 / 阶跃），拟合 rmse |
| 错峰 | 间隔（秒，注明原片帧率） |
| 光/模糊 | 有没有、数值、只在哪 |
| 声音 | 这一刻有没有音效、对齐哪个操作 |
| Remotion 实现 | 用哪个积木/怎么写；需要的 props |
| 难度 | 易 / 中 / 难（走哪一档，见 fallback-ladder.md） |
| 置信度 | 高 / 中 / 低，逐项写（例：上升曲线=高；通知位移=低（看不清）） |
```
每个视频另写三节：开头「编目 vs 实测」更正表、末尾「全片通用规律」（3–10 条，能当规范用）、「没能确认的点」清单。规律汇总到 `references/principles.md` 时带上来源与置信度。

## 7. 入库：做积木 + 必须做独立像素检验
1. 按技法卡写积木（参数用秒，颜色做成 props，随机用 `mulberry32(seed)`，不用 `Math.random`/`Date`；英文示例文案；不加说明小字），在 `src/motion/<组>/` 下，登记到 `registryMeta.ts` + `registry.ts`（两半都要加，编译器会查），新积木在 `public/sfx/block_sfx_map.json` 加事件（`scripts/make_block_sfx_map.py` 生成）。
2. 做一个校准用小合成（Verify fixture：积木单独放在平底上），渲染后用**同一套 ffmpeg + numpy 测量**量我们的渲染和原片，生成 `out/motionlab/<批>/VERIFY.md`。现成的写法参考 你的Remotion工程 `scripts/verify_batch3a.py`、`verify_batch3b.py`。
3. **每行标独立性**（先看这一列再信绿色）：

| 标注 | 含义 | 能证明什么 |
|---|---|---|
| IND | 参数来自技法卡/默认值，源数值在这里重新从像素量出 | 真正的检验：卡片对不对 |
| CARD | 把卡片模型直接算出来（不渲染）去比实测 | 卡片本身错多少 |
| FIT / CAL | 参数拟合到这段原片，再从渲染量回来 | 只证明实现没走样，**不是**独立证据 |
| SEMI | 参数来自卡片表，而卡片作者就是读这段原片得到的；我重新独立量了原片 | 半独立 |
| T / [T] | 原片在像素上量不了，只能和卡片读数比（±10–30%） | 几乎不能证明什么 |
| SELF | 渲染链自检（公式 vs 像素），不涉及原片 | 代码对不对 |

4. **先用卡片参数渲一遍、量一遍，存成 `_verify_firstpass.md`**——那是诚实的独立检验记录；之后为了贴合而改参数的行一律改标 FIT。principles.md 第 14 节那 26 条「被推翻的结论」大多就是这样发现的。
5. **校准通过的标准**：偏差 = (我们 − 原片)/原片，±15%；基数很小的行用绝对容差（时间 ±0.1–0.15s 或原片 1 帧；位置 ±1.5 字；隔帧素材 max(15%, 6px)）。报告里分开写「IND 行几行通过」和「FIT 行几行通过」，只有 IND 行能说「原片数值对」。超差行保留并解释（例：Counter 到终值 0.53 vs 0.43s，原片跟数据走，我们 ease 减速——OUT 照写）。

## 8. 并排对照图
`$S/side_by_side.sh out/motionlab/<批>/compare_scroll_A27.4.png src.mp4 27.4 out/x/_full.mp4 3.6 960 540`
- 左原片、右我们，各缩到 960×540（竖屏按原比例，如 406×722）。说明写在文件名里（没有 drawtext）。我们这一侧也可以是 `npx remotion still` 出的 PNG（时间写 `-`）。
- 每张图下面写一行：哪个积木、对标原片哪一秒、看到的差距（字体/质感/位置/节奏）。「约像几成」只在这里由人主观打分，分「动势/时序」与「质感」两项（3B 批的做法）。

## 9. 音频：节拍分析与「卡操作不卡拍」检验
1. 提音频：`ffmpeg -i src.mp4 -vn -ac 1 -ar 22050 a.wav`
2. 先从画面逐帧定出关键操作的时间（点击、回车、落位、切场），列成逗号串。
3. `python3 $S/audio_beat_check.py a.wav --highpass 3000 --events "2.5,5.125,7.72,…"`
   - 输出拍长/BPM、每个事件对最近拍点的偏移、平均绝对偏移 vs 随机预期（拍长/4）、事件 ±0.1s 内有 onset 的比例 vs 随机命中率、静音段。
   - `--highpass 3000`：点击/键击类音效常藏在音乐床下，B 就是高通 3kHz 后才看清。
   - 自动估的拍长可能差 2:3 或 1:2（B 卡片定 0.729s，脚本全频估出 0.489s），拿不准就用 `--period` 两种都跑，结论一致才算数。
   - B 的复测：`--highpass 3000 --period 0.729` → 偏移比值 1.08（不卡拍）；事件 ±0.1s 内有 onset 37% vs 随机 10%（卡操作）。
4. 判读：比值 <0.6 才说「卡拍」；onset 很密（≥2/s）时随机命中率本身就高，命中多也不能下结论（C 的教训，见 principles.md 第 9 节）。节拍自相关强度 <0.1 时结论降级为「中/低」。
5. 「掉电平 → 重击」：看每秒电平，找大转场前 0.1–0.5s 的电平下坑与随后的冲击（A 12.9s 等）。

## 10. 复刻与并排校准的闭环
接到新参考视频：拿素材（第 1 节）→ 通览定位（第 2 节）→ 编目、分组（第 3 节）→ 密集抽帧 + 测量 + 写技法卡（第 4–6 节）→ 先查 `block-catalog.md` 有没有现成积木可调参数（多数新视频只要调参 + Compose 组合）→ 没有才新做积木（第 7 节）→ 首轮渲染、量、写 VERIFY（含 firstpass）→ 并排图（第 8 节）→ 交给用户看样片，按反馈改 → 回写：新规律进 principles.md，新积木 `node $S/gen_catalog.mjs --project <工程目录>` 重新生成目录，被推翻的数值进 principles.md 第 14 节。
